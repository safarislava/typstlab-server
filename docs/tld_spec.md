# Спецификация формата TLD (TypstLab Document Specification)

Настоящий документ содержит формальное описание формата **TLD (TypstLab Document)**, структуры данных, правил представления CRDT-состояния Yjs, форматов передачи через HTTP API и интеграции фронтенда/бэкенда.

---

## 1. Концепция формата TLD (TypstLab Document)

**TLD (TypstLab Document)** — это формат блочного и интерактивного документа платформы TypstLab, спроектированный для совместной работы в реальном времени (Real-Time Collaboration).

### Ключевые принципы TLD:
1. **CRDT как фундамент (Yjs State):**  
   Файл TLD хранится и передается в виде бинарного вектора состояния Yjs (`state BYTEA` / Base64). Это гарантирует автоматическое, математически строгое и бесконфликтное слияние правок от нескольких пользователей.
2. **Клиентская модель блоков и AST:**  
   Вся блочная композиция (ячейки кода Typst, метаданные блоков, визуальные секции) упакована внутри структур данных Yjs (`Y.Array('blocks')`, `Y.Text('block:<id>')`). Сервер не занимается парсингом Typst — он является высокопроизводительным CRDT-релеем и надежным хранилищем.
3. **Локальная WASM-компиляция:**  
   Рендеринг и компиляция документа Typst в PDF / SVG / Canvas выполняются на клиенте через WebAssembly (WASM).

---

## 2. Формат JSON DTO в HTTP API

При запросах `GET /files/typst/{fileID}` и `POST /files/typst/{fileID}/changes` сервер возвращает TLD-файл в следующем формате:

```json
{
  "id": "c30980ef-51eb-47eb-ba05-89416a5db202",
  "project_id": "7a359cf9-e932-473d-9d41-52643a5323bb",
  "name": "document.typ",
  "type": "typst",
  "state": "AQEBCwAAAQ==",
  "updated_at": "2026-09-08T12:00:00Z"
}
```

### 2.1. Спецификация полей
| Поле         | Тип      | Формат                | Описание                                                      |
|:-------------|:---------|:----------------------|:--------------------------------------------------------------|
| `id`         | `string` | `UUIDv4`              | Уникальный идентификатор TLD-файла.                           |
| `project_id` | `string` | `UUIDv4`              | Идентификатор проекта.                                        |
| `name`       | `string` | `string`              | Имя файла с расширением `.typ` или `.tld`.                    |
| `type`       | `string` | `enum`                | Всегда `"typst"`.                                             |
| `state`      | `string` | `Base64`              | Бинарный слепок Yjs-документа (`doc.EncodeStateAsUpdate()`).  |
| `updated_at` | `string` | `ISO 8601 / RFC 3339` | Время последней модификации.                                  |

## 3. Структура документа TLD внутри Yjs (Frontend Data Layout)

Внутри `Y.Doc` данные TLD-документа организуются следующим образом:

```text
Y.Doc
 ├── Y.Array('blocks') -> [ { id: "uuid-1", name: "header" }, { id: "uuid-2", name: "section1" } ]
 ├── Y.Text('block:uuid-1') -> "= Заголовок документа\n#let author = 'Иван'"
 └── Y.Text('block:uuid-2') -> "== Введение\nТекст первого раздела..."
```

* **Массив блоков (`blocks`):** хранит упорядоченный список дескрипторов блоков (порядок следования, UUID, имя/тип блока).
* **Текстовые узлы (`block:<id>`):** хранят исходный текст каждого фрагмента на языке Typst с посимвольным CRDT-отслеживанием правок.

---

## 4. Жизненный цикл изменений (Lifecycle & Synchronization)

1. **Создание TLD-документа:**  
   Клиент инициализирует локальный `Y.Doc`, создает базовую структуру блоков, кодирует в `state` через `Y.encodeStateAsUpdate(doc)` и отправляет в `POST /projects/{projectID}/files`.
2. **Real-time правки (Changes):**  
   При локальном редактировании текста генерируется дельта `update`, которая отправляется на `POST /files/typst/{fileID}/changes`.
3. **Офлайн-синхронизация (Offline Sync):**  
   При выходе из офлайна клиент передает вектор состояния `content_vectors[fileID] = Y.encodeStateVector(doc)` в `POST /projects/{projectID}/sync` и получает недостающую дельту в инструкции `apply_changes`.
